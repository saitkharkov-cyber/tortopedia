## Текущее состояние

Техническая миграция сайта завершена. Production работает на Cloudflare Pages и после последнего push проверен вручную — обновление применилось корректно.

Сайт больше не поддерживается как набор вручную редактируемых HTML-файлов. Источник истины теперь — Eleventy-исходники в `src`.

`src + layouts/partials → npm run build → _site-pilot → publish.ps1 → готовые HTML в корне → GitHub main → Cloudflare Pages`

## Публикация

В корне репозитория есть `publish.ps1`.

Он:

1. запускает `npm run build`;
2. требует ровно 54 HTML-файла;
3. копирует собранные HTML из `_site-pilot` в production-структуру корня;
4. запускает `git diff --check`;
5. показывает `git diff --stat`.

Рабочий цикл теперь:

1. редактировать только `src` и шаблоны;
2. выполнить `./publish.ps1`;
3. посмотреть diff;
4. commit;
5. push в `main`;
6. при важных изменениях проверить production.

Не редактировать готовые HTML в корне как основной источник — они являются результатом сборки.

## Следующий этап: контент

Техническую миграцию считать завершённой.

Следующая задача — развитие контента.

Перед массовым написанием новых материалов желательно сделать редакционный style guide Tortopedia на основе существующих статей. Анализировать несколько характерных статей RU и UA и зафиксировать:

- структуру материала;
- типичные вступления и выводы;
- лексику, фразеологию и степень разговорности;
- формат H2/H3;
- использование списков, инструкций, фото и видео;

Цель — новые статьи должны естественно продолжать старый корпус, а не выглядеть текстами из другого проекта.

## Важно не потерять: responsive images / srcset

Это отдельная незавершённая задача из предыдущего HANDOFF и её нужно сохранить в плане.

Контентные изображения уже переведены в WebP, но полноценные responsive images ещё не сделаны. План:

- определить реальные размеры отображения изображений на мобильных/планшетах/десктопе;
- подготовить уменьшенные WebP-варианты там, где это даёт реальную экономию;
- добавить `srcset`/`sizes` (при необходимости через `<picture>`);
- сначала проверить на одной типичной статье и главной;

- после проверки масштабировать на остальные страницы.

Это не блокирует добавление нового контента, но является следующей заметной задачей по производительности и не должна потеряться.

## Правила безопасности

- сначала локальная сборка, затем проверка HTML, затем commit/push;
- после failed build не доверять старому `_site-pilot`;
- не применять широкие regex/whitespace-замены без проверки;
- для PowerShell-записи использовать UTF-8 без BOM;
- изменения делать test-first на одном типичном материале, затем масштабировать;
- production URL-структуру без причины не менять.
