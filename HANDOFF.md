# HANDOFF — Tortopedia

Дата: 2026-09-06
Ветка: `main`

## Текущее состояние

Техническая миграция завершена. Production работает на Cloudflare Pages. Источник истины — Eleventy-исходники в `src`, готовые HTML в корне являются результатом локальной сборки.

Текущая схема:

`src + layouts/partials → npm run build → _site-pilot → publish.ps1 → production HTML в корне → GitHub main → Cloudflare Pages`

Cloudflare сам Eleventy не собирает.

## Eleventy и публикация

- Eleventy 3.1.6
- input: `src`
- output: `_site-pilot`
- текущая контрольная сборка: **52 HTML-файла**
- `publish.ps1` должен ожидать ровно 52 HTML-файла
- `_site-pilot/`, `node_modules/`, `backup/` игнорируются Git

Количество уменьшилось с 54 до 52 после удаления дублирующей пагинации категории `vse-o-mastike/page/2/` RU/UA.

Рабочий цикл:

1. редактировать `src` и шаблоны;
2. выполнить `./publish.ps1`;
3. проверить diff;
4. commit;
5. push в `main`;
6. при важных изменениях проверить production.

Важно: `publish.ps1` сейчас не очищает `_site-pilot` перед сборкой. Уже был случай, когда удалённые page/2 остались в старом output и были скопированы обратно. Перед изменениями, связанными с удалением страниц, очищать `_site-pilot`; позже можно добавить очистку прямо в скрипт.

## Первичный repo-wide CSS audit — 2026-09-07

Цель — не удалять стили сегодня, а составить список кандидатов для ручной проверки.

Проверены текущая структура `src`, основные Eleventy layouts и актуальная главная. В активных layouts статьи по-прежнему реально используются базовые группы `.site-*`, `.content-area`, `.post`, `.entry-*`, `.widget`, `.widget_search`, `.widget_recent_entries`, `.post-navigation`, `#secondary`; JS-файлы темы `tab.js`, `sameheight.js`, `jquery.sidr.js`, `custom.js` продолжают подключаться, поэтому динамические классы нельзя считать мёртвыми только по отсутствию в статическом HTML.

Важно: `.our-staff` **используется** на текущей главной (`section#staff`), как и `.featured`, `.special`, `.advantages`, `.populargb`, `.banner`, `.intro`. Их не удалять как «старые секции темы» без анализа конкретных подправил.

Предварительные кандидаты на ручную проверку завтра:

- старые testimonial-блоки: `.testimonial*`, `.tabset*` — на актуальной главной такой секции нет;
- старый `.promotional-block*`;
- комментарии: `.comments-area`, `.comment-*`, `.comment-form*`, `.bypostauthor` — комментариев на текущих статических layouts не видно;
- gallery/caption-наследие: `.gallery*`, `.wp-caption*` — проверить по всем статьям, прежде чем удалять;
- старые widget-типы, которых нет в текущих основных layouts: `.widget_calendar*`, `.widget_product_search*`, `.widget_tag_cloud*`, RSS/social/featured/popular widget-варианты;
- contact-form/WPCF7 footer styles — форм на текущем сайте нет, вероятный крупный кандидат;
- WooCommerce-подобные `.woocommerce-product-search` правила — вероятный мёртвый блок;
- старые `.error`, `.search` и form-related стили — проверить наличие соответствующих production/source страниц и возможное использование поисковой формы;
- LightSlider/Sidr vendor CSS **не удалять на первичном проходе**: Sidr точно участвует в мобильном меню; LightSlider связан с главной/баннером и требует проверки JS и desktop homepage;
- legacy utility/fallback rules (`.pull-left`, `.pull-right`, `.dropcap`, `.highlight`, `.format-*`, `.infinite-scroll*`) — ручная проверка по всему `src`.

Методика на завтра:

1. брать один кандидатный блок/семейство;
2. искать его в `src/**/*.html`, `src/_includes/**/*.njk` и JS;
3. учитывать классы, создаваемые JS динамически;
4. удалять только подтверждённо неиспользуемое;
5. после каждой группы запускать локальную визуальную проверку homepage + article + category + about на desktop/mobile;
6. делать небольшие смысловые коммиты, а не один большой purge.
