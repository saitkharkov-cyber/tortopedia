# ChatGPT — основные правила рабочего процесса

> **Точка входа:** любая рабочая сессия Tortopedia всегда начинается с полного чтения `START_SESSION.md`. Уже он определяет, какие документы читать дальше. Этот файл обязателен после `START_SESSION.md`.

---

## 1. Назначение

Этот документ фиксирует короткий набор обязательных правил взаимодействия:

**user → ChatGPT → user**

Главная формула:

**понять → проверить → предложить один шаг → получить подтверждение → изменить минимально → проверить результат → только потом коммит/отправка.**

Подробные пояснения, примеры и исключения находятся в `CHATGPT_WORKFLOW_REFERENCE.md`.

---

## 2. Язык

Основной язык общения и внутренней документации — **русский**.

Англицизмы использовать только там, где они являются буквальными техническими терминами, именами команд, файлов, технологий, API или элементов интерфейса.

Если есть точный и естественный русский эквивалент — использовать его.

---

## 3. Маленькие шаги

По умолчанию работать пошагово:

1. определить текущую точку;
2. предложить один следующий шаг;
3. дождаться подтверждения;
4. выполнить или дать точную команду;
5. проверить результат;
6. перейти дальше.

`+`, `++`, `+++` означают подтверждение **текущего предложенного шага**, а не бессрочное разрешение на последующие действия.

Если пользователь использует `+++` как сигнал «готово, переходи дальше», трактовать его именно как завершение непосредственно предыдущего шага.

---

## 4. Не расширять границы задачи

Не делать «заодно»:

- рефакторинг;
- архитектурные изменения;
- переименования;
- очистку соседнего кода;
- обновление зависимостей;
- исправление посторонних проблем.

Если найдена отдельная проблема — указать её и не исправлять без согласования.

**Минимальное достаточное изменение предпочтительнее большого улучшения.**

---

## 5. Сначала проверка, потом изменение

Если состояние можно проверить — не строить решение на предположении.

Основной источник истины:

1. фактическое состояние файлов и Git;
2. подтверждённые решения текущей сессии;
3. свежий `CURRENT_SESSION_STATE.md`;
4. актуальный `HANDOFF.md`;
5. остальная документация;
6. память о прошлых чатах.

Если память, HANDOFF или документация расходятся с текущими файлами — верить текущим файлам и Git.

---

## 6. PowerShell и ручные правки

Для Windows-проектов команды давать только в fenced-блоках `powershell`.

Жёсткое правило:

**PowerShell-команда по умолчанию должна быть в одну строку.**

Не использовать here-string, если можно обойтись обычной однострочной командой.

Связанные атомарные действия можно объединять через `&&`.

Если нужно изменить файл вручную, явно писать:

> В редакторе открой...

Не смешивать ручную правку с PowerShell.

---

## 7. Git перед коммитом

Перед каждым коммитом обязательно:

```powershell
git diff --check
```

затем просмотр содержательного diff и:

```powershell
git status --short
```

После staging при необходимости обязательно повторить проверку уже индексированных изменений:

```powershell
git diff --cached --check
```

Добавлять в индекс конкретные файлы. Без необходимости не использовать:

```powershell
git add .
```

или:

```powershell
git add -A
```

Намеренно неотслеживаемые файлы не добавлять, не удалять и не «чистить».

---

## 8. Главенство пользователя при коммите и отправке

Коммит и отправка изменений в удалённый репозиторий выполняются **только по явной команде пользователя**.

ChatGPT может:

- предложить коммит;
- подготовить команду;
- предложить сообщение;
- проверить diff и Git status.

Но сам запуск коммита или отправки допустим только после явного разрешения на конкретное действие.

`+`, `++`, `+++` считаются таким разрешением только тогда, когда непосредственно перед ними был предложен именно конкретный коммит или отправка.

Разрешение не переносится автоматически на следующие операции.

---

## 9. Source и сгенерированные файлы

Если проект работает по схеме:

**исходники → сборка → production**

обычно изменяем исходники, затем запускаем сборку/публикацию.

После автоматизации обязательно проверить фактический результат и `git status`.

Успешное завершение команды ещё не означает, что результат правильный.

---

## 10. Старт сессии

Стартовый документ — только:

`START_SESSION.md`

HANDOFF больше не является точкой входа.

В начале любого нового рабочего чата:

1. полностью прочитать `START_SESSION.md`;
2. выполнить указанный там порядок чтения документов;
3. проверить фактическое состояние файлов и Git;
4. только после этого определить один следующий шаг.

Нельзя начинать с памяти или сразу с HANDOFF.

---

## 11. HANDOFF

HANDOFF — документ передачи контекста между чатами или после длительной паузы.

Он отвечает на вопрос:

> Где мы остановились и что делать дальше?

В начале HANDOFF должна быть короткая инструкция:

> **Начни с `START_SESSION.md`.**

HANDOFF не должен дублировать общий стартовый регламент.

Во время активной сессии HANDOFF постепенно теряет силу: новые подтверждённые изменения имеют приоритет.

Перед переходом в новый чат или длительную паузу HANDOFF обновляется по текущему состоянию.

---

## 12. Защита от внезапного разрыва чата

Нельзя надёжно предсказать достижение лимита длины чата.

Поэтому во время длинной **активной** сессии используется:

`CURRENT_SESSION_STATE.md`

Это короткая живая контрольная точка текущей работы.

### Контроль включается в начале сессии

`START_SESSION.md` обязан явно напомнить о необходимости следить за `CURRENT_SESSION_STATE.md` на протяжении всей активной работы.

ChatGPT не должен просто «помнить, что правило существует». Он обязан регулярно проверять, не пора ли обновить контрольную точку.

Обновлять её во время активной работы:

- после заметного этапа;
- после важного решения;
- после коммита/отправки, если работа в этой сессии продолжается;
- перед рискованной длинной серией действий;
- перед паузой, после которой планируется продолжить текущую сессию;
- когда накопилось много нового контекста;
- если с последнего обновления произошло несколько значимых изменений.

После каждого заметного этапа ChatGPT должен мысленно проверить:

> Если чат оборвётся прямо сейчас, `CURRENT_SESSION_STATE.md` позволит без догадок продолжить работу?

Если нет — самому предложить обновление контрольной точки.

Пользователь не обязан напоминать об этом.

Если работа на текущий период **завершается** и прямо сейчас готовится актуальный HANDOFF для следующего чата или длительной паузы, отдельное финальное обновление `CURRENT_SESSION_STATE.md` не требуется: оно будет дублировать тот же итоговый снимок.

Практическое правило:

- сессия продолжается → `CURRENT_SESSION_STATE.md`;
- сессия завершается и контекст передаётся дальше → `HANDOFF.md`.

После внезапного разрыва приоритет:

1. файлы и Git;
2. свежий `CURRENT_SESSION_STATE.md`;
3. актуальный `HANDOFF.md`;
4. документация;
5. память.

---

## 13. Локальная структура Tortopedia и документация

Основной и единственный локальный Git-репозиторий:

```text
D:\Git\tortopedia
```

Документация хранится внутри него:

```text
D:\Git\tortopedia\docs
```

`docs/` является обычной частью основного репозитория `saitkharkov-cyber/tortopedia` и отслеживается тем же Git.

Отдельный Git-репозиторий для документации не используется.

Все Git-команды выполняются из корня проекта:

```text
D:\Git\tortopedia
```

Документация не должна попадать в production-сборку сайта. При текущей схеме Eleventy входной каталог — `src`, поэтому `docs/`, находящаяся вне `src/`, в сборку не входит.

---

## 14. Пауза означает паузу

Если пользователь говорит:

- «стоп»;
- «подожди»;
- «пока не делай»;
- «останавливаемся»;

дальнейшие действия по этой ветке прекращаются.

---

## 15. Один ответ — один основной шаг

В пошаговом режиме не давать длинную цепочку команд наперёд.

По умолчанию:

- краткое объяснение;
- один следующий шаг;
- одна команда или одна ручная правка.

Исключение — пользователь явно просит полный план.

---

## 16. Большие копипаст-блоки

Если пользователь просит цельный текст для копирования целиком — документ, большой Markdown-фрагмент, конфиг, шаблон, инструкцию или другой многострочный блок — выдавать его **одним непрерывным fenced-блоком**.

Если внутри такого текста уже используются тройные обратные кавычки, внешний блок оборачивать в **четыре обратные кавычки**, чтобы внутренние Markdown-блоки не разрывали ответ.

Пример принципа:

```text
внутри большого блока могут находиться обычные тройные fenced-блоки
```

Не разбивать один предназначенный для копирования текст на несколько отдельных блоков интерфейса.

Это правило действует по умолчанию для Tortopedia, если пользователь просит:

- «цельным блоком»;
- «для копипаста»;
- «дай весь файл»;
- «дай готовый Markdown»;
- «дай целиком».

Главный принцип:

**один логически цельный текст для вставки = один копируемый блок.**

---

## 17. Не выдавать непроверенное за готовое

Нельзя говорить «готово», «исправлено», «всё работает», если результат ещё не проверен.

Правильнее:

> изменение внесено; теперь проверим результат.

---

## 18. Codex

Codex пока не входит в стандартный рабочий процесс.

Если возникнет реальная задача, где он даст явное преимущество, его использование сначала согласовывается отдельно.

После появления практики оформить отдельный `CODEX_WORKFLOW.md`.

---

## 19. Документация — часть проекта

Повторяющиеся полезные правила выносить из чатов в документацию.

Важное знание не должно существовать только в истории переписки.

Все изменения общего порядка старта должны отражаться прежде всего в `START_SESSION.md`, а уже затем — в правилах и справочнике.

---

## Короткая формула

**Всегда начинать с `START_SESSION.md`.**

**Не угадывать то, что можно проверить.**

**Не менять то, что пользователь не просил менять, без согласования.**

**Не коммитить и не отправлять изменения без явной команды пользователя.**

**Во время длинной активной сессии не забывать обновлять `CURRENT_SESSION_STATE.md`.**
