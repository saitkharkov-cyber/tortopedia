# Tortopedia — DEPLOYMENT

## Production

Сайт:

```text
https://tortopedia.in.ua/
```

Репозиторий:

```text
saitkharkov-cyber/tortopedia
```

Production branch:

```text
main
```

Cloudflare Pages автоматически публикует сайт после push в `main`.

---

## Схема публикации

Текущая схема:

```text
src/
→ Eleventy
→ _site-pilot/
→ publish.ps1
→ production HTML в корне проекта
→ GitHub main
→ Cloudflare Pages
→ tortopedia.in.ua
```

Cloudflare Pages используется как площадка публикации готового статического сайта.

Структура HTML и Eleventy-сборка формируются локально, а не на стороне Cloudflare.

---

## Eleventy

Конфигурация:

```text
input:  src
output: _site-pilot
```

Редактируемый контент, шаблоны и partials находятся в:

```text
src\
```

Каталог:

```text
_site-pilot\
```

является промежуточным результатом сборки и не должен использоваться как самостоятельный источник истины.

---

## Локальная сборка

Из корня проекта:

```text
D:\Git\tortopedia
```

выполнить:

```powershell
npm run build
```

После сборки проверить:

- что Eleventy завершился без ошибок;
- что `_site-pilot/` содержит ожидаемые страницы;
- что новые или изменённые страницы присутствуют в сборке;
- что нет неожиданно пропавших страниц.

---

## Подготовка production HTML

Для переноса результатов Eleventy в production используется:

```text
publish.ps1
```

Запуск:

```powershell
.\publish.ps1
```

Скрипт:

- выполняет Eleventy-сборку;
- динамически получает список сгенерированных HTML-файлов;
- проверяет защитный минимальный порог количества HTML;
- копирует HTML из `_site-pilot/` в production-пути проекта;
- копирует `llms.txt`;
- выполняет `git diff --check`;
- показывает `git diff --stat`.

Успешное выполнение `publish.ps1` не означает автоматического разрешения на commit или push.

После него обязательно проверить фактический diff.

---

## Проверка перед коммитом

Сначала:

```powershell
git diff --check
```

Затем:

```powershell
git status --short
```

Просмотреть содержательные изменения:

```powershell
git diff
```

или только нужные файлы:

```powershell
git diff -- path/to/file1 path/to/file2
```

Если в рабочем дереве есть посторонние изменения, не использовать без необходимости:

```powershell
git add .
git add -A
```

Предпочтительно добавлять конкретные файлы.

После staging:

```powershell
git diff --cached --check
git diff --cached --name-status
```

При необходимости:

```powershell
git diff --cached
```

---

## Коммит

Commit выполняется только после явного подтверждения пользователя.

Пример:

```powershell
git add file1 file2 && git commit -m "Описание изменений"
```

Один коммит должен соответствовать одной логической задаче.

Не смешивать без причины:

- контент;
- инфраструктуру;
- документацию;
- рефакторинг;
- исправления другой задачи.

---

## Публикация

Push выполняется только после явного подтверждения пользователя:

```powershell
git push origin main
```

После push дождаться завершения Cloudflare Pages deployment.

## Проверка production после deploy

Минимальный smoke-test:

- открыть `/`;
- открыть `/uk/`;
- открыть изменённую русскую страницу;
- открыть соответствующую украинскую страницу, если она изменялась;
- проверить Console на JavaScript errors;
- проверить Network на 404/5xx для локальных CSS/JS/images;
- убедиться, что главные слайдеры работают на обеих языковых главных, если изменение могло их затронуть.

Если изменялись SEO-элементы, дополнительно проверить:

- `<title>`;
- H1;
- canonical;
- hreflang;
- внутренние ссылки;
- sitemap;
- robots;
- отсутствие неожиданных изменений URL.

---

## Карты сайта и GSC

Если опубликована новая индексируемая страница:

1. добавить её в соответствующий HTML sitemap;
2. добавить URL в корневой `sitemap.xml`;
3. после deploy проверить production URL;
4. при необходимости отправить URL через Google Search Console → «Проверка URL» → «Запросить индексирование».

Сам `sitemap.xml` уже зарегистрирован в Google Search Console.

Повторно добавлять его как новый sitemap после каждой статьи не требуется.

## Responsive images

Responsive images подготавливаются до публикации и проверяются локально.

Для одинакового изображения разных физических размеров использовать:

```html
srcset
sizes
```

с реальными `w`-дескрипторами.

Типичный набор для контентных изображений:

```text
480w / 865w / 1200w / master
```

Конкретный набор зависит от:

- реальной ширины изображения в макете;
- разрешения исходника;
- качества исходника;
- практической пользы дополнительного размера.

Типовой `sizes`:

```html
sizes="(max-width: 865px) 100vw, 865px"
```

`<picture>` использовать только если действительно меняется источник:

- другой кроп;
- другой формат;
- другая композиция;
- другое изображение для отдельного диапазона.

Не использовать схему `1x / 2x / 3x` как основной стандарт для обычных контентных изображений.

## Локальное обновление после изменений в GitHub

Если изменения были сделаны напрямую в GitHub, из:

```text
D:\Git\tortopedia
```

выполнить:

```powershell
git pull origin main
```

Затем:

```powershell
git status --short
```

Перед продолжением работы должно быть понятно, какие локальные изменения уже существуют и относятся ли они к текущей задаче.

## Документация

Рабочая документация находится в:

```text
D:\Git\tortopedia\docs
```

Она отслеживается тем же Git, что и сайт.

`docs/` находится вне `src/`, поэтому при текущей конфигурации Eleventy не попадает в production-сборку.

Изменения документации не требуют запуска Eleventy, если они не затрагивают файлы сайта.

---

## Основной принцип

Production должен быть результатом проверяемой локальной сборки.

Перед публикацией должно быть возможно проверить:

```text
исходники → сборку → production HTML → diff → commit → push → production
```

Cloudflare Pages публикует уже подготовленный результат и не является источником структуры сайта.
