# ChatGPT — справочник по рабочему процессу

> **Как использовать этот файл:** это не стартовый документ. Любая сессия начинается с `START_SESSION.md`, затем обязательно читается `CHATGPT_WORKFLOW_RULES.md`. К этому справочнику обращаться по мере работы, когда возникает соответствующая ситуация (Git, HANDOFF, контрольная точка, большой diff, сгенерированные файлы, Codex и т. п.).

---

Этот документ содержит подробные пояснения к `CHATGPT_WORKFLOW_RULES.md`.

Основной файл правил должен оставаться коротким и обязательным. Здесь хранятся расширенные правила, примеры, исключения и практические сценарии.

---

## 1. Как работать маленькими шагами

Предпочтительный цикл:

1. понять текущую точку;
2. проверить фактическое состояние;
3. предложить один ограниченный шаг;
4. получить подтверждение;
5. выполнить изменение;
6. проверить результат;
7. только после этого двигаться дальше.

Такой режим снижает риск накопить несколько ошибок сразу и упрощает откат.

Подтверждение `+`, `++`, `+++` относится только к тому действию, которое было предложено непосредственно перед ним.

Если пользователь использует `+++` после выполнения предложенного действия, это может означать «готово, переходи к следующему шагу».

---

## 2. Границы задачи

Если запрос звучит как «исправить один блок», это не разрешение:

- менять соседнюю архитектуру;
- переименовывать сущности;
- обновлять зависимости;
- очищать старый код;
- исправлять другие найденные проблемы.

Отдельную проблему лучше зафиксировать одной фразой:

> Вижу ещё одну проблему, но она не относится к текущей задаче. Пока не трогаем.

---

## 3. Основной источник истины

При конфликте источников ориентироваться в таком порядке:

1. фактические файлы;
2. Git;
3. подтверждённые изменения текущей сессии;
4. свежий `CURRENT_SESSION_STATE.md`;
5. актуальный `HANDOFF.md`;
6. остальная документация проекта;
7. память о прошлых чатах.

Если существует возможность быстро проверить факт командой или чтением файла — проверка предпочтительнее воспоминания.

---

## 4. Новый чат

Новый чат не должен начинаться с немедленных изменений и не должен начинаться с HANDOFF.

Единственная точка входа:

`START_SESSION.md`

Порядок:

1. полностью прочитать `START_SESSION.md`;
2. полностью прочитать `CHATGPT_WORKFLOW_RULES.md`;
3. если существует `CURRENT_SESSION_STATE.md` — прочитать его;
4. если работа продолжается из предыдущего чата или после длительной паузы — прочитать актуальный `HANDOFF.md`;
5. сверить документацию с файлами и Git;
6. определить один следующий шаг.

`CHATGPT_WORKFLOW_REFERENCE.md` читается не целиком автоматически, а по необходимости.

Если задача контентная, после общего старта прочитать `TORTOPEDIA_CONTENT_STYLE_GUIDE.md`.

## 5. HANDOFF подробнее

### 5.1. Что это

HANDOFF — документ передачи контекста между чатами или после длительной паузы.

Он должен отвечать:

> Где мы остановились и что делать следующим шагом?

HANDOFF не является стартовым регламентом.

В начале HANDOFF достаточно жёсткого напоминания:

> **Начни с `START_SESSION.md`.**

### 5.2. Что включать

- проект и репозиторий;
- ветку;
- важные пути;
- сделанное;
- проверенное;
- незавершённое;
- известные риски;
- намеренно неотслеживаемые файлы;
- важные команды;
- текущую задачу;
- один следующий шаг.

HANDOFF не должен превращаться в полный журнал истории и не должен повторять общий стартовый порядок.

### 5.3. Когда он теряет силу

После начала активной сессии новые подтверждённые действия постепенно делают HANDOFF устаревшим.

Пример:

HANDOFF говорит, что файл ещё не опубликован. В текущем чате публикация уже выполнена и проверена.

После этого возвращаться к старому пункту HANDOFF нельзя.

### 5.4. Когда обновлять

- перед переходом в новый чат;
- перед длительной паузой;
- после крупного этапа, если работа на текущий период заканчивается и контекст передаётся дальше.

## 6. CURRENT_SESSION_STATE.md

Это страховка от непредсказуемого разрыва длинного чата.

Контроль `CURRENT_SESSION_STATE.md` включается **в начале сессии через `START_SESSION.md`** и остаётся активным до завершения работы.

Рекомендуемый шаблон:

```text
# CURRENT SESSION STATE

Дата:
Проект:
Ветка:
Последний коммит:

## Сейчас сделано
...

## Текущее состояние Git
...

## Решения этой сессии
...

## Что намеренно не трогаем
...

## Текущая задача
...

## Следующий единственный шаг
...
```

Файл должен быть коротким.

Его задача — сохранить последнюю устойчивую точку, а не пересказать весь чат.

ChatGPT обязан сам отслеживать необходимость обновления. Пользователь не должен напоминать.

Проверять необходимость обновления:

- после заметного этапа;
- после важного решения;
- перед длинной или рискованной серией действий;
- после commit/push, если текущая сессия продолжается;
- перед паузой внутри текущей сессии;
- после накопления большого объёма нового контекста;
- если с последнего обновления прошло несколько значимых изменений.

После заметного этапа полезно задавать себе контрольный вопрос:

> Если чат оборвётся сейчас, этого файла достаточно, чтобы продолжить без догадок?

Если нет — предложить обновить его сейчас.

Если работа на текущий период заканчивается и сразу готовится актуальный HANDOFF, отдельное финальное обновление `CURRENT_SESSION_STATE.md` не требуется.

## 7. Язык общения

Основной язык — русский.

Предпочтительно:

- «рабочий процесс», а не `workflow`;
- «границы задачи», а не `scope`;
- «контрольная точка», а не `checkpoint`;
- «основной источник истины», а не `source of truth`;
- «сгенерированный файл», а не `generated file`.

Не переводятся команды, код, имена файлов, названия технологий и те технические термины, где перевод ухудшает точность.

## 8. PowerShell

### 8.1. Формат

Все команды:

```powershell
...
```

По умолчанию одна команда — одна строка.

Предпочтительно:

```powershell
git add file1 file2 && git commit -m "Message"
```

если это один согласованный атомарный шаг.

Не использовать here-string без реальной необходимости.

### 8.2. Редактор и консоль

Если изменение нужно сделать вручную:

> В редакторе открой `path/to/file`.

HTML, CSS, JS и PHP-фрагменты не подавать как будто это PowerShell-команды.

## 9. Git перед началом работы

После стартового чтения документации и до заметной новой задачи перейти в корень проекта:

```text
D:\Git\tortopedia
```

Проверить:

```powershell
git status --short
```

При необходимости:

```powershell
git log --oneline --decorate -3
```

Документация хранится в `docs/` и отслеживается тем же Git, поэтому отдельного Git-контекста для документации нет.

Все проверки выполняются из корня основного репозитория.

---

## 10. Git перед коммитом

Обязательная проверка:

```powershell
git diff --check
```

Затем содержательный diff:

```powershell
git diff -- path/to/file1 path/to/file2
```

И статус:

```powershell
git status --short
```

Для уже добавленных в индекс изменений:

```powershell
git diff --cached --check
```

При необходимости:

```powershell
git diff --cached
```

---

## 11. Добавление файлов в индекс

Предпочтительно:

```powershell
git add file1 file2 file3
```

Не использовать без необходимости:

```powershell
git add .
```

или:

```powershell
git add -A
```

Особенно если в рабочем дереве есть:

- миграционные скрипты;
- временные файлы;
- отладочные файлы;
- локальные конфиги;
- лишние изображения;
- изменения из другой задачи.

---

## 12. Коммит и отправка

Это действия под контролем пользователя.

ChatGPT может предложить:

```powershell
git add ... && git commit -m "..."
```

но не должен выполнять коммит сам без явной команды.

То же относится к:

```powershell
git push origin main
```

Примеры явного разрешения:

- «коммить»;
- «делай коммит»;
- «пушь»;
- «компуш»;
- `++` или `+++`, если непосредственно перед этим был предложен конкретный коммит или push.

Разрешение действует только на текущую операцию.

---

## 13. Коммиты

Один коммит — одна логическая задача.

Не смешивать без причины:

- контент;
- инфраструктуру;
- рефакторинг;
- исправление другой ошибки;
- временные скрипты.

Маленькие понятные коммиты предпочтительнее одного большого смешанного.

---

## 14. Сгенерированные файлы

Если проект построен по схеме:

**исходники → сборка → production**

ручная правка обычно делается в исходниках.

После этого выполняется сборка/публикация.

Сгенерированный файл вручную править только тогда, когда проект этого действительно требует.

После сборки проверить:

- ожидаемые файлы;
- содержательный diff;
- `git status`;
- отсутствие неожиданных изменений.

---

## 15. Большой diff

Большой diff не обязательно означает большую смысловую правку.

Причины могут быть:

- переформатирование;
- окончания строк;
- финальный перевод строки;
- работа генератора;
- перестройка HTML.

Поэтому `git diff --check` не заменяет просмотр содержимого diff.

---

## 16. После автоматизации

Успешное выполнение скрипта не считается достаточной проверкой.

Если запускался build/import/publish/migration, проверить:

- что появился нужный результат;
- что он оказался в правильном месте;
- что не возникли лишние изменения;
- что показывает Git.

---

## 17. Собственные ошибки ChatGPT

Если обнаружена ошибка:

1. назвать её прямо;
2. проверить последствия;
3. предложить минимальное исправление;
4. не оправдывать ошибку длинным текстом.

Если одна и та же ошибка повторилась несколько раз, нужно проверить не только поведение, но и документацию: возможно, правило недостаточно заметно активируется в рабочем процессе.

Пример:

> Да, здесь я ошибся: потерян `<` перед `p`. Исправляем только исходник и повторяем публикацию.

---

## 18. Не выдавать непроверенное за выполненное

Вместо:

> Всё исправлено.

лучше:

> Правка внесена. Теперь проверим сборку.

И только после проверки:

> Проверено, работает.

---

## 19. Пауза

Команды пользователя «стоп», «подожди», «останавливаемся», «пока не делай» немедленно прекращают дальнейшее развитие текущей ветки работы.

---

## 20. Архитектурный долг

Если при локальной задаче найден архитектурный недостаток:

1. зафиксировать его;
2. не смешивать с текущей правкой;
3. вынести в отдельную задачу.

Пример: отсутствие автоматического создания каталогов в publish-скрипте — отдельная инфраструктурная задача.

---

## 21. Документация и локальная структура

Если одно и то же правило повторяется в нескольких чатах и реально помогает работе, оно должно быть вынесено в файл документации.

Единственная точка входа:

- `START_SESSION.md`.

Основные документы:

- `CHATGPT_WORKFLOW_RULES.md`;
- `CHATGPT_WORKFLOW_REFERENCE.md`;
- `CURRENT_SESSION_STATE.md`;
- `HANDOFF.md`;
- `TORTOPEDIA_CONTENT_STYLE_GUIDE.md`;
- `CONTENT_PLAN.md`;
- при необходимости отдельные `PUBLISH_WORKFLOW.md`, `SEO_GUIDE.md`, `CODEX_WORKFLOW.md`.

### Локальное расположение

Основной и единственный Git-репозиторий:

```text
D:\Git\tortopedia
```

Документация:

```text
D:\Git\tortopedia\docs
```

`docs/` является обычной частью основного репозитория `saitkharkov-cyber/tortopedia`.

Документация отслеживается тем же Git, что и сайт. Отдельной Git-истории для `docs/` нет.

Все Git-команды выполняются из корня:

```text
D:\Git\tortopedia
```

Документация не должна попадать в production-сборку сайта.

При текущей схеме Eleventy входной каталог — `src`, поэтому `docs/`, находящаяся вне `src/`, в сборку сайта не входит.

## 22. Codex

Пока не используется как стандартный инструмент.

Не проектировать правила вокруг гипотетического использования заранее.

Когда появится реальная потребность:

1. согласовать применение;
2. попробовать на конкретной задаче;
3. оценить результат;
4. только после практики задокументировать отдельный процесс.

---

## 23. Хороший рабочий цикл

1. ChatGPT начинает с `START_SESSION.md`.
2. Читает обязательные документы по его инструкции.
3. Включает активный контроль `CURRENT_SESSION_STATE.md`.
4. Проверяет фактические файлы и Git.
5. Пользователь формулирует или уточняет задачу.
6. ChatGPT предлагает один минимальный шаг.
7. Пользователь подтверждает.
8. Выполняется изменение.
9. Проверяется результат.
10. После заметного этапа проверяется необходимость обновить `CURRENT_SESSION_STATE.md`.
11. При необходимости исправляется результат.
12. Проверяется diff.
13. Пользователь разрешает коммит.
14. Выполняется коммит.
15. Если сессия продолжается — снова проверить необходимость обновить `CURRENT_SESSION_STATE.md`.
16. Пользователь разрешает отправку.
17. Выполняется отправка.
18. Проверяется синхронизация.
19. Если работа продолжается — обновить контрольную точку при необходимости.
20. Если работа завершается и контекст передаётся следующему чату — обновить HANDOFF.

---

## 24. Антипаттерны

Не делать:

- начинать новый чат сразу с HANDOFF, минуя `START_SESSION.md`;
- помнить про `CURRENT_SESSION_STATE.md` только в конце чата;
- ждать, пока пользователь сам напомнит обновить контрольную точку;
- «заодно» менять соседние файлы;
- автоматически коммитить и отправлять;
- использовать `git add .` при посторонних файлах;
- делать большой рефакторинг внутри локальной задачи;
- править сгенерированный файл вместо исходника без причины;
- продолжать после команды «стоп»;
- удалять неотслеживаемые файлы без согласования;
- утверждать результат без проверки;
- задавать вопрос о факте, который только что был установлен;
- выдавать длинную цепочку шагов при пошаговом режиме;
- путать документацию с отдельным Git-репозиторием.

---

## 25. Основные формулы

**`START_SESSION.md` — единственная точка входа.**

**Не угадывать то, что можно проверить.**

**Минимальное согласованное изменение лучше большого улучшения.**

**CURRENT_SESSION_STATE.md — живая страховка активной сессии.**

**HANDOFF — передача контекста, а не стартовый регламент.**

**Право на коммит и отправку принадлежит пользователю.**
