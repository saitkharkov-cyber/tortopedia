## Что уже сделано

### Восстановление и очистка

Старый WordPress-архив преобразован в обслуживаемый статический сайт. Проверены внутренние href/src и CSS `url(...)` ссылки.

Удалены ненужные обращения к WordPress runtime, включая старые `admin-ajax.php` и oEmbed/wp-json discovery-зависимости. Статические формы поиска оставлены как часть исходной разметки, но полноценного WordPress-поиска на статическом сайте нет.

### CSS и кодировка

Одинаковый большой inline CSS был вынесен из HTML в `/tortopedia.css`.

На всех HTML-страницах добавлен UTF-8 charset.

Для `/wp-content/themes/bakes-and-cakes/images/banner-bg-top.png` добавлен preload, чтобы уменьшить визуальную задержку появления декоративной части шапки.

### Favicon/manifest

Обнаружены сотни версионных копий favicon/manifest-файлов. Они были побайтно проверены, ссылки заменены на канонические файлы, дубликаты удалены.

### Изображения

Контентные JPG/JPEG из uploads преобразованы в WebP с ImageMagick, качество 82.

Контентные PNG из uploads также преобразованы в WebP после отдельной проверки.

HTML/CSS ссылки были заменены только там, где соответствующий WebP реально существовал.

После проверки отсутствия ссылок старые JPG/JPEG/PNG из uploads были удалены.

Размер рабочего дерева существенно уменьшился, а загрузка страниц стала заметно быстрее.

### Slider-библиотеки

`lightslider.js` изначально был подключён почти везде, хотя реальный главный слайдер есть только на:
- `/index.html`;
- `/uk/index.html`.

Подключение LightSlider оставлено только на этих двух страницах.

`jquery.flexslider.js` был подключён на всех страницах, но реальных `#carousel`, `#staff-slider` и других FlexSlider-элементов в HTML не найдено. Библиотека удалена.

В `custom.js` удалены мёртвые вызовы FlexSlider и неиспользуемых LightSlider-элементов. Вызов `#slider` защищён проверкой наличия элемента и `e.fn.lightSlider`.

### jQuery

После очистки slider-зависимостей в Console стали хорошо видны ошибки `jQuery is not defined` на внутренних страницах.

Проверка показала, что основной jQuery был подключён только на 8 из 54 HTML-страниц. Он был добавлен на остальные 46 страниц абсолютным путём:

`/wp-includes/js/jquery/jquery.js`

После этого количество HTML с jQuery стало 54, а ошибки `jQuery is not defined` на проверенной внутренней странице исчезли.

## Текущая архитектура

Сайт остаётся статическим. WordPress как движок не возвращается.

Production-схема:

`локальная рабочая копия → GitHub main → Cloudflare Pages → tortopedia.in.ua`

В перспективе допускается Eleventy (11ty), но только как локальный генератор. Принцип:

`исходники/шаблоны → локальная сборка → проверка итогового HTML → GitHub → Cloudflare Pages`.

Cloudflare не должен быть единственным местом, где генерируется итоговый HTML.

## Новый приоритет: SEO-техническая ревизия

По данным Google Search Console сайт сохраняет поисковый трафик и хорошие позиции, поэтому перед архитектурными изменениями нужно стабилизировать существующий SEO-фундамент.

Следующий порядок работ:

1. Проверить дубли URL вида `/slug/index/` и определить, почему они доступны Google.
2. Настроить корректные 301 на канонические URL без `/index/`, если это подтверждается фактической схемой URL.
3. Проверить `canonical` на русских и украинских страницах.
4. Проверить `hreflang` между RU и UA версиями.
5. Проверить `sitemap.xml`.
6. Проверить `robots.txt`.
7. Проверить внутренние ссылки на старые/дублирующие URL.
8. После изменений проверить Search Console и production.

Не менять существующие успешные URL без необходимости.

## Responsive images — обязательное направление

Следующий этап работы с контентными изображениями — перейти от одного файла на изображение к responsive images.

Правила:
- если композиция одна и та же, использовать `img` + `srcset` + `sizes`;
- минимально предусматривать варианты 1x / 2x / 3x;
- типовой ориентир для контентных изображений: `480w / 960w / 1440w`, если исходник позволяет;
- конкретные размеры выбирать по фактической ширине изображения в макете;
- `<picture>` использовать только при отдельном мобильном кропе, другом формате или иной композиции;
- не оборачивать каждый `<img>` в `<picture>` механически;
- сохранять явные `width` и `height`, корректный `alt`;
- изображения ниже первого экрана — `loading="lazy"`, при необходимости `decoding="async"`.

Эту схему желательно автоматизировать при будущем переходе на 11ty, но её можно внедрять и до него поэтапно.

## Что делать после SEO-ревизии

После стабилизации URL и SEO-разметки:

1. Взять одну реальную статью как пилот.
2. Выделить общий шаблон и контент.
3. Собрать её локально через 11ty.
4. Сравнить итоговый HTML с текущей страницей.
5. Проверить сохранение URL, canonical/hreflang, мета-тегов, структуры и внешнего вида.
6. Только после успешного пилота принимать решение о переносе остальных страниц.

## Правило продолжения

Перед массовыми заменами или удалением ресурсов:
1. определить фактические ссылки;
2. проверить обе языковые версии;
3. сделать локальный тест;
4. посмотреть `git diff --stat` и `git diff --check`;
5. только затем коммитить и публиковать.

Перед локальной работой после изменений, внесённых напрямую в GitHub:

```powershell
git pull origin main
```

Затем:

```powershell
git status
```

Ожидаем чистое рабочее дерево.
