# ARTICLE PRODUCTION REGULATION

## Назначение

Этот документ задаёт обязательный порядок подготовки, сборки, публикации и проверки каждой новой статьи Tortopedia.

Главная цель — убрать плавающую последовательность действий и исключить пропуски обязательных этапов.

Творческая свобода допускается внутри текста, структуры материала и визуальной подачи, но сам производственный процесс статьи должен идти по регламенту.

---

## Главное правило

Нельзя переходить к следующему этапу, пока обязательные пункты текущего этапа не выполнены.

Нельзя считать статью готовой только потому, что написан текст.

Статья считается завершённой только после прохождения полного цикла от решения `GO` до production-проверки и Git-фиксации.

---

## Этапы производства статьи

### 1. Выбор темы и подтверждение самостоятельного интента

Новая статья не создаётся только потому, что тема кажется подходящей или присутствует в старом backlog.

Перед переходом к `post_id`, структуре и написанию текста тема должна пройти полный предварительный анализ.

#### 1.1. Проверка внутренней структуры Tortopedia

- [ ] Проверить `docs/CONTENT_PLAN.md`
- [ ] Проверить `docs/CONTENT_MAP.md`
- [ ] Проверить существующие статьи сайта
- [ ] Найти страницы с тем же или близким интентом
- [ ] Проверить риск каннибализации
- [ ] Определить место нового материала в существующем кластере
- [ ] Определить предполагаемые внутренние связи с существующими материалами

#### 1.2. Проверка поискового спроса

- [ ] Проверить имеющиеся данные Keyword Planner
- [ ] При необходимости проверить старое семантическое ядро
- [ ] При наличии релевантных данных проверить GSC
- [ ] Выделить основной запрос
- [ ] Выделить близкие запросы и подинтенты
- [ ] Не считать близкие формулировки автоматически отдельными интентами

#### 1.3. Проверка актуального SERP

Перед утверждением темы обязательно проверить актуальную поисковую выдачу по основному запросу и важным близким формулировкам.

- [ ] Проверить основной запрос
- [ ] Проверить несколько наиболее важных близких запросов
- [ ] Определить, какие типы страниц преобладают в выдаче
- [ ] Определить фактический пользовательский интент по SERP
- [ ] Проверить, объединяет ли поисковая выдача близкие запросы или разводит их
- [ ] Зафиксировать повторяющиеся смысловые блоки и вопросы, которые действительно ожидает пользователь
- [ ] Не копировать структуру конкурентов механически

#### 1.4. Граница будущей статьи

До создания структуры письменно определить:

- [ ] основной интент статьи;
- [ ] что именно статья должна дать пользователю;
- [ ] какие подинтенты допустимо раскрыть внутри неё;
- [ ] что статья намеренно не должна раскрывать;
- [ ] с какими существующими страницами Tortopedia она потенциально пересекается;
- [ ] чем новая страница будет отличаться от этих материалов.

#### 1.5. Определение формата материала

На основании интента и SERP определить подходящий формат:

- [ ] практическая инструкция / мастер-класс;
- [ ] статья-хаб;
- [ ] справочная статья;
- [ ] подборка идей;
- [ ] рецепт;
- [ ] другой формат, если его требует интент.

Формат определяется задачей пользователя и SERP, а не заранее выбранным шаблоном статьи.

#### 1.6. Решение GO / NO-GO

Тема получает статус `GO`, только если одновременно выполнены условия:

- подтверждён самостоятельный поисковый интент;
- существует достаточное основание для отдельной страницы;
- понятна граница с существующими материалами Tortopedia;
- риск каннибализации контролируем;
- понятна роль статьи в структуре сайта;
- определён подходящий формат материала.

Если самостоятельность интента не подтверждена, новая статья не создаётся. Информацию следует добавить в существующий материал либо оставить тему в backlog до появления дополнительных данных.

**Результат этапа:** решение `GO / NO-GO` и коротко зафиксированный паспорт будущей статьи:

- основной интент;
- основной запрос;
- близкие запросы / подинтенты;
- формат материала;
- роль в кластере;
- пересечения с существующими страницами;
- границы материала — что входит и что не входит.

#### 1.7. Хранение паспорта статьи

После решения `GO` утверждённый паспорт статьи является обязательным рабочим результатом этапа 1.

При создании source-файла статьи паспорт фиксируется непосредственно в нём как служебный блок `ARTICLE_PASSPORT` в формате JSON внутри HTML-комментария.

`ARTICLE_PASSPORT`:

- не является Schema.org-разметкой;
- не является пользовательским контентом;
- не должен отображаться на странице как видимый контент;
- хранится и версионируется вместе с source-файлом статьи;
- служит постоянной точкой фиксации утверждённого интента, границ и роли материала.

До создания source-файла утверждённый паспорт считается рабочим результатом этапа 1 и переносится в `ARTICLE_PASSPORT` при создании source после назначения `post_id`.

По мере прохождения следующих этапов в паспорт могут добавляться утверждённые постоянные рабочие данные, например `post_id`, URL и другие идентификаторы статьи.

RU и UA версии одной статьи должны содержать согласованные значения всех общих для языковой пары данных паспорта.

---

### 2. Идентификатор статьи

`post_id` назначается только после получения статуса `GO` на этапе 1.

- [ ] Найти максимальный глобальный `post_id` по всем существующим source-материалам
- [ ] Проверить отсутствие дублей `post_id`
- [ ] Новый `post_id = max + 1`
- [ ] Убедиться, что новый ID ещё нигде не используется
- [ ] Один и тот же `post_id` использовать для RU и UA версии одной статьи
- [ ] Зафиксировать назначенный `post_id` в рабочем плане статьи

Нельзя резервировать `post_id` для темы, которая ещё не прошла этап 1 и не получила статус `GO`.

**Результат этапа:** подтверждённый глобально уникальный `post_id`, закреплённый за RU/UA парой новой статьи.

### 3. План статьи и SEO-каркас

К планированию статьи переходить только после статуса `GO` и назначения `post_id`.

Структура должна строиться из утверждённого интента и границ материала, а не из желания охватить максимально возможное количество ключевых слов.

#### 3.1. SEO-каркас

До написания основного текста определить:

- [ ] рабочий RU slug / URL;
- [ ] рабочий UA slug / URL;
- [ ] RU H1;
- [ ] UA H1;
- [ ] RU `seo_title`;
- [ ] UA `seo_title`;
- [ ] RU `seo_description`;
- [ ] UA `seo_description`;
- [ ] основной запрос;
- [ ] близкие запросы и формулировки, которые естественно раскрываются внутри материала.

`seo_title`, H1 и description не должны превращаться в перечень ключевых слов. RU и UA формулируются естественно для соответствующего языка, а не механически копируются друг из друга.

#### 3.2. Структура материала

- [ ] Сформировать предварительную структуру H1/H2/H3
- [ ] Для каждого крупного раздела понимать, какую задачу пользователя он решает
- [ ] Проверить, что структура полностью закрывает основной интент
- [ ] Проверить, что структура не выходит за утверждённые границы статьи
- [ ] Убрать блоки, которые создают ненужное пересечение с другими материалами
- [ ] Не добавлять раздел только ради наличия поискового запроса
- [ ] Не копировать структуру конкурентов из SERP

Структура может изменяться во время написания, если это улучшает материал, но изменение не должно нарушать утверждённую границу интента.

#### 3.3. Внутренняя перелинковка

До написания определить:

- [ ] с каких существующих страниц должна появиться ссылка на новый материал;
- [ ] на какие существующие статьи должен ссылаться новый материал;
- [ ] естественные анкоры и контекст этих ссылок;
- [ ] место одной естественной контекстной ссылки на основную категорию;
- [ ] связь с родительским хабом, если статья является дочерним материалом.

Не добавлять внутреннюю ссылку только потому, что страницы принадлежат одной категории. Между ними должна существовать смысловая связь.

#### 3.4. Предварительный визуальный план

На уровне структуры определить:

- [ ] нужен ли hero;
- [ ] какие смысловые места потенциально требуют изображения;
- [ ] где изображения ориентировочно располагаются относительно H2/H3.

На этом этапе не требуется заранее знать окончательную композицию или визуальную задачу каждого изображения. Детальное решение может появиться только после первой генерации.

#### 3.5. Потенциальные товары Tortopedia-shop

При планировании материала отмечать товары, потребность в которых естественно возникает из практической задачи читателя.

- [ ] есть ли в статье естественная потребность в конкретном товаре;
- [ ] какую практическую задачу он решает;
- [ ] есть ли домашняя или более простая альтернатива;
- [ ] уместно ли предложить готовый товар как удобный вариант, а не как обязательную покупку.

Если такая возможность найдена, товар заносится в docs/TORTOPEDIA_SHOP_ASSORTMENT.md, а в source-файле статьи после его создания фиксируется в FrontMatter через shop_opportunities.

Наличие shop_opportunities не является основанием для искусственного добавления товара в текст статьи.

**Результат этапа:** утверждённый SEO-каркас, структура H1/H2/H3, схема внутренней перелинковки, предварительная карта визуальных мест статьи и, если обнаружены, зафиксированные потенциальные товарные возможности.

### 4. Фактчек и практическая проверка

Фактчек проводится до финализации текста и повторно при появлении в процессе написания новых технических утверждений.

Не каждое предложение требует внешнего источника. Проверять в первую очередь утверждения, ошибка в которых может привести к неправильному результату, испорченному изделию или вводящему в заблуждение совету.

#### 4.1. Что проверять

- [ ] Технологические утверждения
- [ ] Свойства ингредиентов и материалов
- [ ] Совместимость материалов и техник
- [ ] Температуры, время, пропорции и другие числовые рекомендации
- [ ] Условия хранения, сушки, охлаждения и транспортировки
- [ ] Утверждения о пищевой безопасности
- [ ] Спорные или неоднозначные рекомендации
- [ ] Советы, результат которых существенно зависит от состава продукта или условий работы

#### 4.2. Источники

- [ ] Использовать надёжные источники
- [ ] Для спорного утверждения по возможности проверять более одного независимого источника
- [ ] Предпочитать первичные, профессиональные или технически компетентные источники
- [ ] Не считать повторение одного утверждения множеством сайтов самостоятельным подтверждением
- [ ] Отделять подтверждённый факт от практического опыта, варианта исполнения или редакционной рекомендации Tortopedia

Названия внешних источников не переносить в пользовательский текст статьи без необходимости. Источники используются прежде всего для проверки корректности материала.

#### 4.3. Практическая реализуемость

Для инструкций и мастер-классов отдельно проверить:

- [ ] Можно ли реально выполнить описанное действие в домашних условиях
- [ ] Не пропущен ли необходимый промежуточный шаг
- [ ] Соответствуют ли инструменты и материалы описанной технике
- [ ] Не противоречат ли разные части инструкции друг другу
- [ ] Соответствуют ли будущие иллюстрации описываемой технологии
- [ ] Не выглядит ли декоративное решение красиво на изображении, но технически бессмысленно в реальной работе

Если предлагается несколько способов, не объявлять один из них универсально лучшим без достаточного основания.

#### 4.4. Ограничения и вариативность

Не придумывать универсальные нормы там, где результат зависит от:

- состава продукта;
- производителя;
- размера изделия;
- толщины слоя;
- температуры и влажности;
- используемой техники;
- условий хранения или транспортировки.

В таких случаях формулировать рекомендацию как ориентир и прямо указывать существенную зависимость от условий.

Если надёжно подтвердить утверждение невозможно, его необходимо убрать, смягчить, обозначить как практический вариант, а не установленный факт, либо явно указать существующую неопределённость.

**Результат этапа:** технически правдоподобный и практически выполнимый материал без неподтверждённых категоричных утверждений.

### 5. RU-версия

RU-версия создаётся только в `src/`.

Production HTML вручную не редактировать. Все изменения должны попадать в production через Eleventy build и установленный процесс публикации.

#### 5.1. Source-файл

- [ ] Создать source-файл `src/.../index.html`
- [ ] Использовать утверждённый RU slug
- [ ] Проверить соответствие расположения файла будущему публичному URL
- [ ] Не копировать старую статью целиком без проверки её front matter и устаревших конструкций

При использовании существующей статьи как технического шаблона брать за основу актуальный материал того же типа.

#### 5.2. Front matter

Проверить и заполнить необходимые поля:

- [ ] `layout`
- [ ] `title`
- [ ] `seo_title`
- [ ] `description`
- [ ] `lang`
- [ ] `permalink`
- [ ] `canonical`
- [ ] `hreflang_ru`
- [ ] `hreflang_uk`
- [ ] `lang_switch_url`
- [ ] `post_id`
- [ ] `published`
- [ ] `category_slug`
- [ ] `prev_url`
- [ ] `prev_title`

Если на этапе 3.5 зафиксированы потенциальные товарные возможности:

- [ ] добавить в Front Matter shop_opportunities по схеме из docs/TORTOPEDIA_SHOP_ASSORTMENT.md;
- [ ] переносить только уже зафиксированные opportunities, а не придумывать их на этапе создания source;
- [ ] если товарных возможностей нет, поле shop_opportunities не добавлять.

Если конкретный тип материала требует дополнительных полей, использовать актуальную структуру соответствующего layout/template, а не добавлять поля по памяти.

Не добавлять вручную данные, которые уже централизованно формируются layout, include или Eleventy-конфигурацией.

#### 5.3. Текст

- [ ] Написать материал по утверждённому плану
- [ ] Соблюдать `docs/TORTOPEDIA_CONTENT_STYLE_GUIDE.md`
- [ ] Сохранять утверждённый поисковый интент и границы материала
- [ ] Не расширять статью посторонними блоками только ради объёма
- [ ] Не превращать текст в механическое перечисление ключевых запросов
- [ ] Проверить последовательность практических действий
- [ ] Проверить соответствие H2/H3 утверждённой структуре
- [ ] Если структура существенно изменилась во время написания, повторно проверить интент и риск пересечения с другими материалами

Текст должен в первую очередь решать задачу читателя. SEO-запросы используются как данные о потребности пользователя, а не как фразы, которые необходимо вставить заданное количество раз.

#### 5.4. Внутренняя перелинковка

- [ ] Добавить предусмотренные планом внутренние ссылки
- [ ] Проверить релевантность анкоров
- [ ] Добавить одну естественную контекстную ссылку на основную категорию
- [ ] Если материал является дочерним — добавить естественную связь с родительским хабом
- [ ] Не дублировать одну и ту же ссылку без смысловой необходимости
- [ ] Проверить хлебные крошки со ссылкой на основную категорию

Обратные ссылки из существующих материалов добавляются на этапе навигации / перелинковки после создания обеих языковых версий.

#### 5.5. Изображения

На этапе первоначального создания RU-файла допускаются предусмотренные структурой места для будущих изображений.

После выбора и подготовки изображений:

- [ ] Указать `image_src`
- [ ] Указать `image_width`
- [ ] Указать `image_height`
- [ ] Указать `image_alt`
- [ ] Вставить утверждённые inline-изображения в предусмотренные смысловые места
- [ ] Проверить, что подписи и окружающий текст соответствуют фактическому содержанию изображения

Не менять текст инструкции только для того, чтобы оправдать ошибочно сгенерированное изображение. Если изображение противоречит материалу, исправляется изображение.

#### 5.6. Предварительная проверка RU source

До перехода к UA-версии:

- [ ] Проверить front matter
- [ ] Проверить H1/H2/H3
- [ ] Проверить отсутствие случайных template markers и черновых заметок
- [ ] Проверить внутренние URL
- [ ] Проверить соответствие текста утверждённому интенту
- [ ] Проверить отсутствие очевидных технических противоречий
- [ ] Проверить сохранение файла в UTF-8 без нежелательного BOM

**Результат этапа:** законченная RU source-версия статьи, готовая служить содержательной основой для подготовки UA-версии и последующей визуальной сборки.

---

### 6. UA-версия

UA-версия обязательна для каждой новой статьи.

Нельзя откладывать её «на потом» и публиковать новую RU-статью как завершённый материал без подготовленной UA-пары.

UA-версия создаётся только в `src/uk/`.

#### 6.1. Source-файл

- [ ] Создать `src/uk/.../index.html`
- [ ] Использовать утверждённый UA slug
- [ ] Использовать тот же `post_id`, что и у RU-версии
- [ ] Проверить соответствие расположения source-файла будущему публичному UA URL
- [ ] Использовать актуальную RU-версию как содержательную основу, но не копировать её механически

#### 6.2. Front matter

Проверить и заполнить необходимые поля:

- [ ] `layout`
- [ ] `title`
- [ ] `seo_title`
- [ ] `description`
- [ ] `lang`
- [ ] `permalink`
- [ ] UA `canonical`
- [ ] `hreflang_ru`
- [ ] `hreflang_uk`
- [ ] обратный `lang_switch_url`
- [ ] тот же `post_id`
- [ ] `published`
- [ ] `category_slug`
- [ ] UA `prev_url`
- [ ] UA `prev_title`

Если RU-версия содержит shop_opportunities:

- [ ] добавить shop_opportunities в UA Front Matter;
- [ ] сохранить те же product, context и status;
- [ ] проверить совпадение shop_opportunities в RU/UA паре.

Дополнительные поля определяются актуальным layout/template соответствующего типа материала.

Не добавлять вручную данные, которые уже централизованно формируются Eleventy, layout или include.

#### 6.3. Адаптация текста

UA-версия должна передавать тот же интент, факты, практическую инструкцию и смысловую структуру, что и RU-версия, но формулироваться естественно для украинского языка.

- [ ] Перевести и адаптировать H1
- [ ] Адаптировать `seo_title`
- [ ] Адаптировать `description`
- [ ] Перевести и адаптировать весь пользовательский текст
- [ ] Сохранить фактическую последовательность инструкций
- [ ] Сохранить утверждённые границы материала
- [ ] Проверить естественность украинской терминологии
- [ ] Не переносить русские синтаксические конструкции механически
- [ ] Не калькировать RU ключевые фразы, если украинский поисковый или языковой вариант формулируется иначе
- [ ] Проверить единообразие терминов внутри всей статьи

UA-версия не обязана быть пословно идентична RU. Допустима естественная языковая адаптация, если фактическое содержание и поисковый интент остаются эквивалентными.

Нельзя самостоятельно добавлять в одну языковую версию новые факты, советы или этапы инструкции, отсутствующие в другой версии, без проверки необходимости такого расхождения.

#### 6.4. Внутренняя перелинковка

- [ ] Все внутренние ссылки по возможности ведут на соответствующие UA-страницы
- [ ] Проверить UA анкоры
- [ ] Добавить одну естественную контекстную ссылку на основную UA-категорию
- [ ] Если материал является дочерним — использовать UA-версию родительского хаба
- [ ] Проверить хлебные крошки со ссылкой на основную UA-категорию
- [ ] Не оставлять RU URL там, где существует соответствующая UA-страница

Если UA-аналога целевой страницы действительно нет, отдельно решить, нужна ли ссылка на RU-материал. Не подменять отсутствующий UA URL вымышленным адресом.

#### 6.5. Изображения

RU и UA могут использовать одни и те же изображения, если сами изображения не содержат языкового текста.

После подготовки визуалов:

- [ ] Использовать корректный `image_src`
- [ ] Проверить `image_width`
- [ ] Проверить `image_height`
- [ ] Подготовить естественный UA `image_alt`
- [ ] Проверить alt каждого inline-изображения
- [ ] Проверить соответствие изображения окружающему UA-тексту
- [ ] Проверить отсутствие русского текста внутри изображения, если изображение используется в обеих версиях

`image_alt` переводится по смыслу изображения, а не механически с RU.

#### 6.6. Сверка RU ↔ UA

До перехода к визуальной генерации / финальной сборке проверить пару страниц:

- [ ] одинаковый `post_id`
- [ ] взаимные canonical/hreflang корректны
- [ ] language switch ведёт RU ↔ UA
- [ ] основной интент одинаков
- [ ] практические шаги не противоречат друг другу
- [ ] фактические утверждения совпадают
- [ ] структура логически эквивалентна
- [ ] внутренние ссылки локализованы
- [ ] категория соответствует языковой версии
- [ ] нет случайно оставшихся фрагментов другого языка
- [ ] файл сохранён в UTF-8 без нежелательного BOM

**Результат этапа:** готовая RU/UA пара одной статьи с единым `post_id`, эквивалентным содержанием, корректной языковой адаптацией и локализованной внутренней перелинковкой.

### 7. План изображений и поиск визуального решения

Работа с изображениями в Tortopedia является итерационной.

Не требуется заранее знать окончательную композицию изображения, полный набор деталей или точное визуальное решение. Часто подходящий вариант можно определить только после первой генерации и визуальной оценки результата.

Поэтому процесс строится так:

**предварительная идея → черновая генерация → оценка → корректировка → повторная генерация / редактирование → утверждение.**

#### 7.1. Предварительный визуальный план

После подготовки текста определить только первоначальную потребность статьи в изображениях:

- [ ] hero image;
- [ ] примерные места inline-изображений;
- [ ] какой фрагмент статьи потенциально нуждается в визуальной поддержке;
- [ ] примерное соотношение сторон;
- [ ] есть ли изображения, которые должны быть связаны между собой.

На этом этапе не требуется окончательно определять точную композицию, все декоративные элементы, окончательный ракурс, количество мелких деталей, точное расположение объектов или окончательный набор inline-изображений.

Количество изображений также может изменяться по мере работы.

Ориентир:

- короткая статья — hero + 1–2 inline;
- средняя статья — hero + 2–3 inline;
- длинный практический материал — hero + 3–5 inline или больше, если изображения действительно помогают читателю.

Это ориентир, а не обязательная норма.

#### 7.2. Первая генерация

Для предполагаемого изображения сформулировать исходную идею и подготовить первоначальный промпт.

Промпт должен быть достаточно конкретным, чтобы получить осмысленный вариант, но не обязан заранее описывать окончательное изображение.

Допускается:

- пробовать разные композиции;
- менять ракурс;
- менять количество и расположение декоративных элементов;
- искать визуальную идею непосредственно через генерацию;
- использовать ChatGPT и Gemini для получения разных интерпретаций одной темы.

Не требуется создавать формальное количество вариантов или промптов, если это не помогает поиску решения.

Первая генерация считается рабочим эскизом и не обязана быть пригодна для публикации.

#### 7.3. Визуальная оценка

После получения изображения пользователь и ChatGPT оценивают фактический результат.

Проверить:

- [ ] подходит ли сама идея;
- [ ] соответствует ли изображение теме и окружающему тексту;
- [ ] что в изображении получилось удачно и должно быть сохранено;
- [ ] что необходимо удалить;
- [ ] что необходимо добавить;
- [ ] что необходимо заменить;
- [ ] что необходимо переместить;
- [ ] нужно ли изменить композицию или ракурс;
- [ ] нет ли визуальных артефактов;
- [ ] нет ли технически невозможных или бессмысленных деталей;
- [ ] выглядит ли результат реалистично для домашнего кондитера;
- [ ] соответствует ли изображение позиционированию Tortopedia.

На этом этапе допускается изменение первоначальной визуальной идеи.

Если после просмотра изображения становится понятно, что другой визуальный подход лучше решает задачу статьи, первоначальный план не является обязательным.

#### 7.4. Итерационная корректировка

После оценки выбрать дальнейшее действие:

- отредактировать существующее изображение;
- изменить отдельные элементы;
- существенно изменить композицию;
- подготовить новый промпт;
- сгенерировать изображение заново;
- попробовать альтернативный вариант в другой модели;
- отказаться от изображения, если оно не приносит материалу пользы.

Цикл **генерация → оценка → корректировка** повторяется столько раз, сколько необходимо для получения подходящего результата.

Не нужно сохранять неудачное решение только потому, что оно соответствовало первоначальному плану.

#### 7.5. Связанные изображения

Если несколько изображений показывают один торт, объект или последовательность действий, после появления удачного базового варианта определить, какие характеристики необходимо сохранять между кадрами.

Например:

- форма и пропорции торта;
- цвет покрытия;
- используемый материал;
- основные декоративные элементы;
- конструкция отдельных деталей;
- логика последовательности действий.

Не требуется обеспечивать абсолютную визуальную идентичность кадров, если это не важно для понимания материала.

Но изображения не должны противоречить друг другу или создавать впечатление технологически разных процессов там, где показывается один мастер-класс.

#### 7.6. Утверждение визуального решения

Изображение считается выбранным только после явного подтверждения пользователя.

До подтверждения оно остаётся рабочим вариантом и может быть изменено или заменено.

**Результат этапа:** выбранные пользователем изображения и утверждённые визуальные решения для hero и необходимых inline-позиций.

### 8. Финальная подготовка и интеграция изображений

К технической подготовке изображения переходить только после утверждения его визуального содержания.

Для каждого утверждённого изображения:

- [ ] выполнить необходимые финальные исправления;
- [ ] проверить отсутствие заметных артефактов;
- [ ] проверить техническую правдоподобность;
- [ ] проверить соответствие тексту статьи;
- [ ] определить финальное соотношение сторон;
- [ ] подготовить WebP;
- [ ] сделать необходимые размеры;
- [ ] использовать понятное SEO-friendly имя файла;
- [ ] подготовить RU alt;
- [ ] подготовить естественный UA alt;
- [ ] скопировать файлы в `wp-content/uploads/YYYY/MM/`;
- [ ] вставить изображение в RU;
- [ ] вставить изображение в UA;
- [ ] проверить правильность `src`, `srcset`, размеров и других используемых атрибутов;
- [ ] проверить фактическое отображение после build.

Для hero дополнительно:

- [ ] указать корректные `image_src`, `image_width`, `image_height`, `image_alt`;
- [ ] проверить использование hero в карточке категории;
- [ ] проверить использование hero на главной, если статья туда попадает;
- [ ] проверить использование hero в Open Graph / social meta.

#### Важное правило

Текст и изображение должны соответствовать друг другу, но при конфликте нельзя автоматически переписывать корректную практическую инструкцию под ошибочно сгенерированную картинку.

Сначала определить, что правильно с точки зрения содержания статьи.

Если ошибочно изображение — исправляется изображение.

Если визуальная работа выявила реальную ошибку или неясность в тексте — исправляется текст с повторной проверкой RU и UA версий.

**Результат этапа:** окончательно подготовленный комплект изображений, технически интегрированный в обе языковые версии статьи.

### 9. Навигация между статьями

После создания RU и UA версий новой статьи обновить линейную навигацию между материалами.

Линейная навигация `prev / next` и контекстная внутренняя перелинковка — разные механизмы.

`prev / next` обеспечивает последовательную навигацию между опубликованными материалами. Контекстные ссылки определяются смысловой связью статей и планируются отдельно.

#### 9.1. Новая статья

Для RU:

- [ ] указать корректный `prev_url`;
- [ ] указать корректный `prev_title`.

Для UA:

- [ ] указать UA `prev_url`;
- [ ] указать UA `prev_title`.

RU и UA должны ссылаться на соответствующую языковую версию предыдущего материала.

#### 9.2. Предыдущая статья

В предыдущей статье добавить обратную навигацию на новую.

Для RU:

- [ ] `next_url` новой RU-статьи;
- [ ] `next_title` новой RU-статьи.

Для UA:

- [ ] `next_url` новой UA-статьи;
- [ ] `next_title` новой UA-статьи.

Не считать задачу выполненной после добавления `prev` только в новую статью.

#### 9.3. Проверка цепочки

- [ ] новая RU → предыдущая RU;
- [ ] предыдущая RU → новая RU;
- [ ] новая UA → предыдущая UA;
- [ ] предыдущая UA → новая UA;
- [ ] заголовки соответствуют фактическим страницам;
- [ ] URL не перепутаны между языковыми версиями;
- [ ] ссылки ведут на существующие source-страницы;
- [ ] после build навигация формируется корректно.

Если существующая логика проекта определяет `prev / next` не по тематическому кластеру, а по общей последовательности публикаций, не менять этот принцип для отдельной статьи.

#### 9.4. Контекстные обратные ссылки

На этом же этапе реализовать предусмотренные планом смысловые ссылки **из существующих материалов на новую статью**.

- [ ] добавить запланированные RU-ссылки;
- [ ] добавить соответствующие UA-ссылки;
- [ ] проверить естественность анкоров;
- [ ] проверить, что ссылка действительно полезна в данном контексте;
- [ ] не добавлять обратные ссылки механически во все статьи одной категории.

Если новая статья является дочерней для существующего хаба, проверить предусмотренную связь **хаб → новая статья → хаб**, если такая двусторонняя связь логически оправдана.

**Результат этапа:** корректная RU/UA цепочка `prev / next` и реализованные запланированные контекстные обратные ссылки на новый материал.

### 10. Категория и автоматический category listing

Карточка новой статьи в категории формируется автоматически Eleventy.

Ручное добавление карточки новой статьи в HTML категории запрещено.

#### 10.1. Привязка статьи к категории

В RU и UA source-файлах проверить:

- [ ] корректный `category_slug`;
- [ ] корректный `lang`;
- [ ] корректный `published`;
- [ ] одинаковый `post_id` RU/UA пары;
- [ ] наличие данных, необходимых шаблону карточки;
- [ ] соответствие выбранной категории утверждённой роли статьи в структуре сайта.

Категория определяется смысловой принадлежностью материала, а не только наличием похожих ключевых слов.

Не создавать дополнительную категорию ради одной статьи без отдельного решения по структуре сайта.

#### 10.2. Source категории

Если для публикации статьи изменение самой страницы категории не требуется, source категории не редактировать.

Не добавлять вручную карточку статьи, ссылку на новую статью, изображение карточки, дату или другие данные, которые уже получает автоматический listing.

Уникальное описание категории, breadcrumbs и другие собственные элементы страницы категории сохраняются независимо от автоматического списка статей.

#### 10.3. Проверка после build

После build открыть соответствующие RU и UA категории в `_site-pilot`.

Для новой карточки проверить:

- [ ] статья появилась автоматически;
- [ ] появилась только один раз;
- [ ] RU-статья находится в RU-категории;
- [ ] UA-статья находится в UA-категории;
- [ ] корректный `post_id`;
- [ ] корректный title;
- [ ] корректный URL;
- [ ] корректное изображение;
- [ ] карточка не содержит фрагментов другого языка;
- [ ] порядок карточек соответствует действующей логике listing.

Отдельно проверить, что публикация новой статьи не привела к исчезновению, дублированию или неправильной сортировке существующих карточек.

Если карточка не появилась или появилась неправильно, исправлять source/front matter или логику Eleventy. Не компенсировать ошибку ручной вставкой карточки в категорию.

**Результат этапа:** новая RU/UA пара автоматически и корректно присутствует в соответствующих категориях без ручного редактирования listing.

### 11. HTML sitemap

HTML sitemap обновляется вручную для каждой новой опубликованной статьи.

Редактировать необходимо source-файл HTML sitemap. Generated / production HTML вручную не изменять.

#### 11.1. Добавление новой статьи

- [ ] Добавить RU-страницу
- [ ] Добавить UA-страницу
- [ ] Использовать фактические публичные URL
- [ ] Использовать корректные пользовательские названия страниц
- [ ] Разместить ссылки в соответствии с действующей структурой HTML sitemap

Не добавлять страницу только в одной языковой версии.

#### 11.2. Проверка source

До build проверить:

- [ ] RU URL присутствует один раз
- [ ] UA URL присутствует один раз
- [ ] отсутствуют дубли
- [ ] URL соответствуют canonical новой статьи
- [ ] названия не перепутаны между языковыми версиями
- [ ] не добавлен URL из `_site-pilot` или другой служебный путь

#### 11.3. Проверка после build

В `_site-pilot` проверить:

- [ ] RU-страница присутствует в HTML sitemap
- [ ] UA-страница присутствует в HTML sitemap
- [ ] обе ссылки ведут на правильные страницы
- [ ] названия отображаются корректно
- [ ] новая запись не нарушила структуру sitemap
- [ ] отсутствуют дубли новой страницы

Если generated HTML sitemap не соответствует source, искать причину в source/template/build. Не исправлять generated-файл вручную.

**Результат этапа:** обе языковые версии новой статьи присутствуют в HTML sitemap с корректными публичными URL и без дублей.

### 12. `llms.njk`

`llms.txt` не является полным sitemap сайта.

Новая статья не добавляется в `llms.njk` автоматически только потому, что она опубликована.

#### 12.1. Решение о добавлении

Для новой статьи определить, должна ли она быть представлена в `llms.txt`.

При принятии решения учитывать:

- [ ] является ли материал важной точкой входа в структуру Tortopedia;
- [ ] представляет ли он значимый тематический раздел или кластер;
- [ ] является ли статья хабом или другим опорным материалом;
- [ ] помогает ли ссылка лучше объяснить структуру и основное содержание сайта;
- [ ] не превращает ли её добавление `llms.txt` в обычный перечень всех опубликованных страниц.

Обычная дочерняя статья или отдельный мастер-класс не обязаны присутствовать в `llms.txt`.

#### 12.2. Если статья добавляется

- [ ] Редактировать только source `llms.njk`
- [ ] Использовать фактический production URL
- [ ] Использовать понятное название / описание материала
- [ ] Соблюдать существующую структуру файла
- [ ] Не дублировать уже существующую ссылку

#### 12.3. Проверка после build

Независимо от решения о добавлении проверить generated `llms.txt`.

Если статья добавлялась:

- [ ] ссылка присутствует;
- [ ] URL корректен;
- [ ] название / описание корректно;
- [ ] дублей нет.

Если принято решение не добавлять статью:

- [ ] убедиться, что публикация не внесла в `llms.txt` неожиданных изменений.

Generated / production `llms.txt` вручную не исправлять.

**Результат этапа:** принято явное решение `добавлять / не добавлять` новую статью в `llms.txt`; при добавлении изменение выполнено через source и проверено после build.

### 16. Публикация в production через `publish.ps1`

К `publish.ps1` переходить только после успешного build и полной проверки `_site-pilot`.

Скрипт публикации переносит проверенный generated-результат в production-структуру репозитория.

Production HTML вручную не редактировать.

#### 16.1. Запуск

Использовать штатный:

`.\publish.ps1`

Если выполнение `.ps1` заблокировано текущей PowerShell ExecutionPolicy, не изменять системную или пользовательскую ExecutionPolicy.

Использовать одноразовый запуск:

`powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\publish.ps1"`

`Bypass` применяется только к данному процессу и не должен использоваться как повод менять постоянные настройки PowerShell.

#### 16.2. Контроль результата скрипта

После выполнения проверить вывод `publish.ps1`.

- [ ] скрипт завершился без ошибок;
- [ ] количество `copied` выглядит ожидаемо;
- [ ] количество `unchanged` выглядит правдоподобно;
- [ ] отсутствуют неожиданные массовые изменения;
- [ ] stale production HTML = 0;
- [ ] нет сообщений об ошибках копирования или удаления.

Если число изменённых файлов существенно больше ожидаемого, не переходить автоматически к Git. Сначала определить причину.

#### 16.3. Проверка production-файлов

До Git staging убедиться, что в production появились ожидаемые изменения:

- [ ] RU HTML новой статьи;
- [ ] UA HTML новой статьи;
- [ ] необходимые изображения;
- [ ] обновлённые предыдущие RU/UA статьи с `next`, если они менялись;
- [ ] обновлённые страницы с контекстными обратными ссылками;
- [ ] соответствующие категории;
- [ ] главная, если новая статья должна на неё попасть;
- [ ] HTML sitemap;
- [ ] `sitemap.xml`;
- [ ] `llms.txt`, только если его source действительно изменялся;
- [ ] другие страницы, которые закономерно пересобрались из-за новой публикации.

Не считать любой изменённый generated-файл автоматически правильным. Его изменение должно объясняться source-изменением или действующей логикой сборки.

После публикации выполнить проверку рабочего дерева.

- [ ] посмотреть `git status --short`;
- [ ] просмотреть общий diff;
- [ ] убедиться, что присутствуют только ожидаемые source, asset и production-изменения;
- [ ] проверить отсутствие случайных временных файлов;
- [ ] проверить отсутствие ненужных generated / служебных файлов;

Если после `publish.ps1` обнаружена содержательная или техническая ошибка:

**source → build → проверка `_site-pilot` → `publish.ps1`**

выполняются повторно для затронутой части.

Не исправлять production HTML вручную вместо исправления source.

**Результат этапа:** проверенное содержимое `_site-pilot` корректно перенесено в production, рабочее дерево содержит только объяснимые изменения, `git diff --check` чистый.

### 17. Git review, staging, commit и push

Git-фиксация выполняется только после успешного build, проверки `_site-pilot`, `publish.ps1` и проверки production diff.

Commit и push не являются автоматическим продолжением публикации.

#### 17.1. Review рабочего дерева

До staging:

- [ ] выполнить `git status --short`;
- [ ] определить назначение каждого изменённого / нового / удалённого файла;
- [ ] убедиться, что все изменения относятся к текущей задаче;
- [ ] проверить отсутствие случайных временных файлов;
- [ ] проверить отсутствие ненужных служебных файлов;
- [ ] проверить отсутствие файлов, которые не должны храниться в репозитории;
- [ ] убедиться, что ожидаемые source, assets и production-файлы действительно присутствуют.

Не использовать `git add .` или аналогичное массовое staging без предварительного понимания состава рабочего дерева.

`docs/HANDOFF.md` и `docs/CURRENT_SESSION_STATE.md` не добавлять автоматически только потому, что они существуют или изменены.

Документы состояния обновляются тогда, когда это действительно требуется рабочим процессом, а `HANDOFF` — прежде всего при завершении / передаче сессии.

#### 17.2. Staging

Добавлять в staging только файлы, относящиеся к текущему логическому изменению.

После staging:

- [ ] выполнить `git status --short`;
- [ ] проверить список staged-файлов;
- [ ] просмотреть `git diff --cached`;
- [ ] убедиться, что staged diff соответствует текущей задаче;
- [ ] убедиться, что в staging нет случайных файлов;
- [ ] убедиться, что необходимые файлы не забыты;
- [ ] при необходимости повторно выполнить `git diff --check`.

Если staged diff слишком велик для надёжной визуальной проверки одним выводом, проверять его по файлам или логическим группам.

#### 17.3. Разрешение на commit

После проверки staged diff показать пользователю итоговое состояние и кратко указать, что именно будет зафиксировано.

Commit выполнять только после явного подтверждения пользователя.

`++`, используемый как подтверждение текущего шага рабочего процесса, считается разрешением на commit только тогда, когда предыдущий шаг прямо сформулирован как запрос разрешения выполнить конкретный commit.

Не интерпретировать более раннее общее согласие на работу как разрешение на будущие commit/push.

#### 17.4. Commit

После разрешения:

- [ ] выполнить commit только проверенного staged diff;
- [ ] использовать короткое содержательное commit message;
- [ ] убедиться, что commit создан успешно;
- [ ] проверить полученный commit / состояние рабочего дерева.

Если после commit обнаружена ошибка, не скрывать её дополнительными несвязанными изменениями. Исправление оформляется осознанно отдельным изменением либо другим явно согласованным способом.

#### 17.5. Push

Push выполнять только для уже проверенного commit и только после разрешения пользователя, если оно не было явно дано одновременно на `commit + push`.

После push:

- [ ] убедиться, что push завершился успешно;
- [ ] проверить соответствие локального `HEAD` и `origin/main`;
- [ ] проверить `git status`;
- [ ] убедиться, что не осталось неожиданных незакоммиченных изменений.

Успешный push ещё не означает завершение публикации статьи. После него обязательна production-проверка.

**Результат этапа:** только проверенные изменения зафиксированы в Git, commit/push выполнены с явного разрешения пользователя, локальная и удалённая ветки находятся в ожидаемом состоянии.

### 18. Production-проверка после push

После успешного push дождаться обновления production и проверить фактически опубликованный сайт.

Проверка `_site-pilot` не заменяет production-проверку.

Нельзя считать статью полностью опубликованной только потому, что build, `publish.ps1` и push завершились успешно.

#### 18.1. Доступность RU и UA

Отдельно проверить production URL обеих версий:

- [ ] RU возвращает HTTP 200;
- [ ] UA возвращает HTTP 200;
- [ ] отсутствует неожиданный redirect;
- [ ] URL соответствует утверждённому canonical;
- [ ] отображается актуальная версия статьи, а не старый или неполный результат публикации.

Если после push production ещё не обновился, не считать это ошибкой статьи до проверки завершения deployment.

#### 18.2. Основные SEO-данные

Для RU и UA проверить в фактически полученном production HTML:

- [ ] `<title>`;
- [ ] meta description;
- [ ] один правильный H1;
- [ ] `post_id`;
- [ ] canonical;
- [ ] `hreflang_ru`;
- [ ] `hreflang_uk`;
- [ ] language switch RU ↔ UA;
- [ ] breadcrumbs.

Не считать наличие тегов достаточным — проверить их значения и URL.

#### 18.3. Изображения

- [ ] hero загружается;
- [ ] inline-изображения загружаются;
- [ ] используются production URL;
- [ ] нет 404 по новым изображениям;
- [ ] размеры / пропорции отображаются корректно;
- [ ] RU alt корректен;
- [ ] UA alt корректен;
- [ ] изображения находятся в правильных местах статьи.

#### 18.4. Навигация и перелинковка

Проверить непосредственно на production:

- [ ] новая RU → предыдущая RU;
- [ ] предыдущая RU → новая RU;
- [ ] новая UA → предыдущая UA;
- [ ] предыдущая UA → новая UA;
- [ ] предусмотренные контекстные ссылки работают;
- [ ] связь с родительским хабом работает, если она предусмотрена;
- [ ] внутренние ссылки не ведут на 404 или неправильную языковую версию.

#### 18.5. Категории и главная

Для RU и UA категорий проверить:

- [ ] новая карточка присутствует;
- [ ] карточка присутствует один раз;
- [ ] title корректен;
- [ ] URL корректен;
- [ ] изображение корректно;
- [ ] язык карточки правильный.

Если статья должна присутствовать среди последних материалов на главной:

- [ ] проверить RU;
- [ ] проверить UA;
- [ ] проверить title, URL и изображение.

#### 18.6. Open Graph / social meta

Для RU и UA проверить production HTML:

- [ ] один `og:title`;
- [ ] один `og:description`;
- [ ] один `og:url`;
- [ ] один `og:image`;
- [ ] `og:url` совпадает с canonical;
- [ ] `og:image` доступен по production URL;
- [ ] используются корректные Twitter/social meta;
- [ ] отсутствуют дубли.

Для статьи с собственным hero проверить, что social meta использует ожидаемое изображение, а не fallback.

При необходимости для важной публикации дополнительно проверить фактический social preview через используемый внешний debugger / preview-инструмент.

#### 18.7. Schema.org

Проверить фактический JSON-LD production-страницы.

Для обычной статьи:

- [ ] `Article`;
- [ ] `BreadcrumbList`;
- [ ] корректные URL;
- [ ] корректные данные текущей языковой версии;
- [ ] отсутствие дублей;
- [ ] синтаксически корректный JSON-LD.

Для специальных типов страниц проверить предусмотренную дополнительную schema-разметку, например `Recipe`.

#### 18.8. Sitemap и служебные файлы

На production проверить:

- [ ] RU URL присутствует в HTML sitemap;
- [ ] UA URL присутствует в HTML sitemap;
- [ ] RU URL присутствует в `sitemap.xml`;
- [ ] UA URL присутствует в `sitemap.xml`;
- [ ] новых URL нет в sitemap дважды;
- [ ] `llms.txt` соответствует решению этапа 12.

#### 18.9. Если production отличается от `_site-pilot`

Не исправлять production-файлы вручную.

Определить источник расхождения:

**source → build → `_site-pilot` → `publish.ps1` → Git → deployment → production.**

После исправления повторить необходимые этапы и заново проверить затронутые production-страницы.

**Результат этапа:** фактически опубликованные RU и UA страницы, их изображения, навигация, категории, metadata, Schema.org и sitemap проверены непосредственно на production.

### 19. Критерии полного завершения статьи

Статья получает статус `DONE` только после прохождения полного цикла производства и публикации.

Успешное написание текста, build, commit или появление страницы на production по отдельности не означают завершение статьи.

Перед присвоением статуса `DONE` подтвердить:

- [ ] тема прошла анализ и получила `GO`;
- [ ] назначен глобально уникальный `post_id`;
- [ ] RU-версия полностью готова;
- [ ] UA-версия полностью готова;
- [ ] RU и UA образуют корректную языковую пару;
- [ ] фактчек завершён;
- [ ] утверждённые изображения подготовлены и интегрированы;
- [ ] `prev / next` работает в обеих языковых версиях;
- [ ] предусмотренная контекстная перелинковка реализована;
- [ ] новая статья автоматически появилась в правильных RU/UA категориях;
- [ ] HTML sitemap обновлён;
- [ ] решение по `llms.txt` принято и выполнено;
- [ ] RU и UA автоматически присутствуют в XML sitemap;
- [ ] `_site-pilot` прошёл полную предпубликационную проверку;
- [ ] Open Graph / social meta проверены;
- [ ] Schema.org проверена;
- [ ] `publish.ps1` выполнен без необъяснимых изменений;
- [ ] production diff проверен;
- [ ] Git staging и staged diff проверены;
- [ ] commit и push выполнены с явного разрешения пользователя;
- [ ] локальная и удалённая ветки находятся в ожидаемом состоянии;
- [ ] production RU проверен;
- [ ] production UA проверен;
- [ ] production категории / главная проверены там, где это применимо;
- [ ] production HTML sitemap и XML sitemap проверены;
- [ ] production Open Graph / social meta проверены;
- [ ] production Schema.org проверена;
- [ ] не осталось известных ошибок или незавершённых обязательных действий по статье.

Если хотя бы один обязательный пункт ещё не выполнен, статья остаётся в статусе `IN PROGRESS`.

Допускается отдельно зафиксировать необязательную будущую работу — например, дополнительный social content, новые иллюстрации, расширение кластера или последующий анализ поисковых данных. Такая работа не блокирует `DONE`, если она не являлась обязательной частью текущей публикации.

`DONE` относится к производственному циклу конкретной статьи и не означает, что материал никогда больше не будет обновляться.

**Результат этапа:** статья полностью опубликована, технически проверена и зафиксирована в Git; обязательных незавершённых действий по текущей публикации нет.

## Запрещённые сокращения процесса

Нельзя сокращать производственный цикл таким образом, чтобы пропускался обязательный контрольный этап или ошибка одного этапа компенсировалась ручным вмешательством на следующем.

Запрещено:

- начинать производство новой статьи до решения `GO`;
- назначать / резервировать `post_id` теме, которая ещё не получила `GO`;
- считать наличие запроса в Keyword Planner достаточным доказательством самостоятельного интента без проверки структуры сайта и актуального SERP;
- создавать отдельную статью без определения её границ относительно существующих материалов;
- расширять статью посторонними блоками только ради охвата дополнительных ключевых запросов;
- пропускать фактчек технических, спорных или потенциально значимых практических утверждений;
- выдавать ориентировочные или зависящие от условий рекомендации за универсальные правила;
- публиковать новую RU-статью без обязательной UA-пары;
- считать UA-версию механическим переводом, не проверяя терминологию, ссылки и фактическое соответствие RU;
- считать первоначальный визуальный план окончательным и сохранять неудачное изображение только потому, что оно соответствует исходному промпту;
- принимать визуально красивое изображение, если оно противоречит тексту, технологии или здравой практической логике;
- переписывать корректную инструкцию только для того, чтобы оправдать ошибочно сгенерированное изображение;
- технически подготавливать и интегрировать изображение до его утверждения пользователем;
- забывать обратный `next` в предыдущей RU/UA статье;
- смешивать линейную навигацию `prev / next` с контекстной внутренней перелинковкой;
- добавлять карточку новой статьи в category listing вручную;
- вручную исправлять generated HTML в `_site-pilot`;
- вручную исправлять production HTML вместо изменения source и повторного build;
- вручную добавлять новую статью в `sitemap.xml`;
- автоматически добавлять каждую новую статью в `llms.txt` без отдельного решения;
- считать успешный build достаточным без проверки `_site-pilot`;
- считать корректный `_site-pilot` достаточным без production-проверки;
- считать наличие Schema.org или Open Graph в общем template доказательством того, что конкретная новая страница сформирована правильно;
- менять постоянную PowerShell ExecutionPolicy ради запуска `publish.ps1`;
- игнорировать неожиданно большой build / publish / Git diff;
- использовать массовый staging без предварительного понимания состава рабочего дерева;
- выполнять commit без проверки staged diff;
- выполнять commit или push без явного разрешения пользователя;
- считать успешный push доказательством успешной production-публикации;
- объявлять статью `DONE`, пока остаётся хотя бы один невыполненный обязательный этап;
- обновлять `HANDOFF` автоматически в середине продолжающейся рабочей сессии без необходимости передачи состояния.

Если обязательный этап был случайно пропущен, необходимо вернуться к нему и затем повторить все последующие проверки, на которые его результат мог повлиять.

Нельзя компенсировать пропущенный этап ручным исправлением конечного результата.

## Рабочий принцип для ChatGPT

При производстве новой статьи ChatGPT ведёт работу строго по этому регламенту сверху вниз.

Главная задача ChatGPT — не просто выполнить отдельную команду, а сохранять правильную последовательность производственного процесса и не допускать незаметного пропуска обязательных этапов.

### Порядок работы

- выполнять только текущий этап;
- не переходить к следующему обязательному этапу до завершения текущего;
- не выдавать сразу цепочку будущих команд, если пользователь не попросил об этом отдельно;
- если этап уже фактически выполнен и проверен в текущей работе, его можно отметить выполненным без искусственного повторения;
- если обнаружен пропущенный обязательный этап, вернуться к нему;
- после исправления ошибки повторить последующие проверки, на которые эта ошибка могла повлиять;
- не объявлять статью `DONE`, пока не выполнены критерии этапа 19.

### Источник истины

При работе с репозиторием фактическое состояние файлов, Git и generated output имеет приоритет над предположениями, памятью и устаревшей документацией.

Перед изменением существующего файла сначала проверить его актуальное содержимое.

Перед использованием команды, пути, front matter field, template или другой технической конструкции, в актуальности которой есть сомнение, сначала проверить текущее состояние проекта.

Не придумывать существование файла, значение `post_id`, URL, slug, front matter field, Git-состояние, результат build, наличие страницы в sitemap или результат production-публикации.

Если это можно проверить по репозиторию или фактическому output, необходимо проверить.

### Работа с RU и UA

RU и UA являются двумя обязательными версиями одного материала.

Нельзя считать проверку одной языковой версии автоматической проверкой второй.

При изменении фактического содержания после подготовки обеих версий проверить, требуется ли соответствующее изменение второй языковой версии.

### Работа с изображениями

ChatGPT не должен предполагать, что первоначальный промпт определяет окончательное визуальное решение.

После каждой рабочей генерации учитывать фактическое изображение и замечания пользователя.

Если пользователь просит сохранить изображение максимально без изменений и изменить конкретный элемент, не расширять объём редактирования без необходимости.

Утверждённым считается только визуальный вариант, явно принятый пользователем.

### Работа с командами

Если пользователь выполняет команды вручную:

- давать один следующий шаг;
- PowerShell-команду давать одной физической строкой;
- не объединять несколько самостоятельных этапов в одну команду без необходимости;
- после результата команды сначала оценить фактический вывод;
- только затем давать следующий шаг.

Не предполагать успешность команды до получения результата.

### Git

Не выполнять и не предлагать как уже разрешённые `commit` / `push`, пока пользователь явно не подтвердил именно этот шаг.

Перед commit обязательно проверить staged diff.

Факт предыдущего согласия с содержанием изменений не является автоматическим разрешением на commit или push.

### Значение `++`

Если пользователь отвечает:

`++`

`+++`

`++++`

это означает:

**текущий предложенный шаг выполнен / утверждён; дать только следующий шаг.**

Такой ответ не является универсальным разрешением на будущие действия.

Если текущий шаг был явно сформулирован как **«после `++` выполнить конкретный commit / push / другое действие»**, тогда `++` является подтверждением именно этого действия.

### Формат взаимодействия

По умолчанию:

**один этап → действие / проверка → результат пользователя → следующий этап.**

Не перегружать пользователя последующими этапами заранее.

Если для принятия решения требуется выбор пользователя, сначала показать варианты и дождаться решения.

Если фактический результат противоречит ожидаемому, исходить из фактического результата, а не продолжать первоначальный план механически.
